# Gym SaaS - PRD

**Version:** 2.0  
**Date:** 2026-03-26  
**Status:** Active Working PRD  
**Purpose:** هذا الـ PRD يصف المرحلة الحالية الواقعية للمشروع كما ينبغي أن تُبنى من الكود الموجود الآن، وليس التصور الكبير المستقبلي فقط.

---

## 1. ملخص المنتج

منتج لإدارة الجيم من خلال لوحة تحكم داخلية تساعد صاحب الجيم أو فريق الاستقبال على إدارة:

- الفروع
- المستخدمين
- الأعضاء
- باقات الاشتراك
- ربط العضو باشتراك
- الحضور بالباركود في المرحلة التالية مباشرة

المرحلة الحالية تستهدف `operational MVP` بسيط ومستقر قبل الدخول في المدفوعات والتقارير والـ integrations.

---

## 2. المشكلة التي يحلها المنتج

المشكلة الأساسية ليست “غياب features كثيرة”، بل غياب نظام بسيط ومستقر يدير العمليات اليومية للجيم:

- إضافة الفروع
- تسجيل العاملين والأعضاء
- إنشاء باقات الاشتراك
- معرفة من له اشتراك فعال ومن لا
- التحضير لنظام حضور بالباركود

---

## 3. الهدف من هذه المرحلة

تحويل المشروع من `prototype` إلى `usable MVP` يمكن تشغيله داخل جيم واحد بشكل منظم.

---

## 4. المستخدمون المستهدفون

### 4.1 Admin / Owner

المستخدم الرئيسي في هذه المرحلة. يملك صلاحية:

- إنشاء وإدارة الفروع
- إنشاء المستخدمين
- إنشاء الأعضاء
- إنشاء الباقات
- إسناد الاشتراكات

### 4.2 Staff / Reception

في المرحلة الحالية دوره المتوقع:

- مراجعة الأعضاء
- تسجيل الحضور لاحقاً
- التعامل مع الباركود بعد إنهاء module الحضور

### 4.3 Manager

دور إداري وسيط موجود في الواجهة الحالية ضمن الأدوار، لكن احتياجاته ما زالت ضمن نفس قدرات الإدارة الأساسية.

---

## 5. نطاق الـ MVP الحالي

## In Scope

1. Authentication
2. Gym bootstrap عند التسجيل
3. Branch management
4. User management
5. Member management
6. Subscription plan management
7. Subscription assignment to member
8. Basic barcode attendance بعد إنهاء الربط

## Out of Scope حالياً

1. Payments and invoices
2. Reports and analytics
3. WhatsApp / SMS / Email notifications
4. Trainer management الحقيقي
5. PT sessions
6. Inventory / POS
7. Mobile apps
8. Advanced multi-tenant SaaS admin

---

## 6. الـ user journey الأساسي

### Journey 1: إنشاء حساب الجيم

1. المستخدم يسجل حساب.
2. النظام ينشئ:
   - `tenant`
   - `default gym`
   - `admin user`
3. المستخدم يعمل `login`.

### Journey 2: تجهيز النظام

1. الـ admin يضيف فرع أو أكثر.
2. الـ admin يضيف مستخدمين حسب الدور.
3. الـ admin يضيف عضو.

### Journey 3: إدارة الاشتراكات

1. الـ admin ينشئ باقة اشتراك.
2. يربط الباقة بعضو.
3. يصبح بالإمكان التحقق من صلاحية العضو.

### Journey 4: الحضور

1. الاستقبال يدخل أو يمسح الباركود.
2. النظام يبحث عن العضو.
3. يتحقق من صلاحية الاشتراك.
4. يسجل عملية الحضور.

## 7. المتطلبات الوظيفية

### 7.1 Authentication

- تسجيل مستخدم جديد
- تسجيل دخول
- جلب المستخدم الحالي من التوكن
- تخزين `gymId` داخل الـ token

### 7.2 Branches

- عرض الفروع
- إنشاء فرع
- تعديل فرع
- حذف فرع

### 7.3 Users

- عرض المستخدمين داخل نفس الجيم
- إضافة مستخدم
- تعديل مستخدم
- حذف مستخدم
- دعم الأدوار الأساسية:
  - `admin`
  - `manager`
  - `staff`
  - `member`
  - `coach` أو `trainer` بعد توحيد التسمية

### 7.4 Members

- إنشاء عضو
- ربط العضو بـ `user` موجود
- حفظ:
  - `barcode`
  - `idNumber`
  - `branchId`
- تعديل العضو
- حذف العضو

### 7.5 Subscription Plans

- إنشاء باقة
- عرض الباقات
- تعديل الباقة
- حذف الباقة

### 7.6 Subscription Assignment

- ربط عضو بباقة
- حفظ:
  - `memberId`
  - `subscriptionId`
  - `startDate`
  - `endDate`
- إتاحة معرفة الاشتراك الحالي للعضو

### 7.7 Attendance

هذه feature المرحلة التالية مباشرة بعد تثبيت الأساس:

- إدخال أو scan باركود
- جلب العضو
- التحقق من وجود اشتراك فعال
- إنشاء attendance record

---

## 8. المتطلبات غير الوظيفية

1. الواجهة يجب أن تظل ثنائية اللغة `Arabic / English`.
2. أي data حساسة يجب ألا تعتمد على mock data في الـ core modules.
3. كل request تخص الجيم يجب أن تكون scoped بـ `gymId`.
4. شكل الـ API response يجب أن يكون موحداً.
5. قاعدة البيانات يجب أن يكون لها schema واضح أو `migrations`.

---

## 9. البيانات الأساسية المطلوبة

من الكود الحالي، الجداول المرجحة في المرحلة الأساسية هي:

- `tenant`
- `gym`
- `branches`
- `users`
- `members`
- `subscription_plans`
- `subscription`

مهم: هذا ليس schema نهائياً، بل ما هو ظاهر من الكود الحالي. يجب تثبيته رسمياً في خطوة مبكرة.

---

## 10. معايير النجاح للمرحلة الحالية

تعتبر هذه المرحلة ناجحة إذا تحقق الآتي:

1. جميع شاشات الـ core تعتمد على API حقيقية وليست mock.
2. يمكن إنشاء وتعديل وحذف:
   - فرع
   - مستخدم
   - عضو
   - باقة اشتراك
3. يمكن ربط عضو باشتراك من الواجهة.
4. لا توجد تناقضات في أسماء الحقول بين الـ frontend والـ backend.
5. يمكن البدء في attendance بدون إعادة تصميم البيانات من الصفر.

## 12. مبدأ مهم

أي feature خارج الـ MVP الأساسي يجب ألا تبدأ قبل إنهاء:

1. توحيد أسماء الحقول
2. توحيد response contract
3. تثبيت schema
4. إنهاء CRUD الأساسية

لأن هذه النقاط هي التي تحدد هل المشروع سيتحول لمنتج حقيقي أم سيظل prototype متشتت.
